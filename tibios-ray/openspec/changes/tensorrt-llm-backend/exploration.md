# Exploration: TensorRT-LLM as a new inference engine/backend for tibios-ray

## Current State

`provider-backend-composition` (archived) wired `ChatProvider`/`EmbeddingProvider`/`RerankProvider` to real backends through `worker.py::build_runtime()` — the sole Composition Root. Architecture, confirmed by reading real code:

- `backends/text.py`'s `TextGenerationBackend(BackendAdapter, Protocol)` is the ONLY execution contract for chat/text-generation: `backend_id`, `supports(plan)`, `acquire(plan)->BackendSession`, `release(session)`, `generate(session, TextRequest)->AsyncIterator[TextChunk]`. Its module docstring already says verbatim: *"the Chat/Reasoning capability's engine-facing contract (llama.cpp, vLLM, TensorRT-LLM in Phase 4)"* — TensorRT-LLM was anticipated, unmodified, from day one.
- Two concrete engines exist as siblings in `engines/`: `LlamaCppTextBackend` (engines/llamacpp.py, per-session pool of N pre-warmed `Llama` instances, thread-bridge streaming) and `VllmTextBackend` (engines/vllm.py, one shared lazily-built `AsyncLLM`, refcounted, natively async streaming with a DELTA `output_kind`). Both satisfy `TextGenerationBackend` structurally — no base class — and both only import from `tibios_ray.backends` (enforced by `tests/unit/engines/test_engines_layering.py`'s AST scan).
- `worker.py::build_runtime()` is the only module constructing concrete engine classes (enforced by a constructor-call AST scan, `provider-backend-composition/spec.md` "Composition Root Exclusive Backend Ownership", corrected in D29 to carve out package-level re-exports in `engines/__init__.py` as non-violating aliasing).
- `config.py` supplies `WorkerConfig` with one optional per-engine dataclass each (`LlamaCppConfig`, `VllmConfig`, `OnnxConfig`×2), all env-var sourced (`TIBIOS_RAY_*`), absent → `None` → engine not built → capability unwired (never a crash). `worker.py`'s `_BACKEND_PREFERENCE: tuple[BackendId,...]` feeds a `PreferenceOrderPolicy` (`selection/preference.py`) — first-match-wins over `ServingConstraints.available_backends`, lexicographic fallback, current order `(vllm, llama_cpp, onnxruntime)`.
- `ChatProvider.execute()` (capabilities/chat.py) was read in full: it has ZERO backend-specific branching. It parses a `ChatRequest`, resolves a model ref, calls `resolve_backend(self.backends, self.selection_policy, model, ...)` (a pure function in `capabilities/dispatch.py`), then only `backend.acquire/generate/release` against the `TextGenerationBackend` Protocol. Adding a fourth entry to `self.backends: Mapping[BackendId, TextGenerationBackend]` requires no Provider code change — confirmed, not assumed.
- Catalog: `catalog/entries/chat.py` and `catalog/entries/vision.py` already list `tensorrt_llm` (`_TENSORRT_LLM = BackendId("tensorrt_llm")`) in several `BackendSupport` rows (large/high-VRAM tiers: Qwen3-8B/32B, Llama-3.3-70B, DeepSeek-V3/R1, Gemma-3-27B, Kimi-K2, Qwen2.5-VL-72B). `catalog/entries/embedding.py` and `rerank.py` have zero `tensorrt` references (confirmed via grep). `CHAT_GENERATE_DESCRIPTOR.backends` in `capabilities/chat.py` and the frozen table in the living `capability-providers/spec.md` ALREADY commit `tensorrt_llm` as a legit backend for `chat.generate` (and `vision.understand`) — this is a pre-existing, asserted-stable spec requirement, not something this change needs to add.
- `capabilities/vision.py`'s `VisionProvider` is still a zero-field, unconditionally-raising Provider (`NoBackendAvailableError`) — deliberately unwired, out of scope of `provider-backend-composition` (its proposal.md explicitly excludes vision/speech/OCR: "backends/ has no execution Protocol at all for vision... engines/ has no concrete adapter for any of the four"). `VISION_UNDERSTAND_DESCRIPTOR.backends` already lists `{vllm, tensorrt_llm}` too, but wiring it needs a whole separate vision Protocol + Provider-wiring change first.
- `pyproject.toml` `[project.optional-dependencies]` shows the established pattern: `llamacpp = ["llama-cpp-python>=0.3.34,<0.4"]`, `vllm = ["vllm>=0.9.0,<0.10; python_version < '3.14'"]` (with a documented CUDA/torch-pin marker rationale), `onnx = [...]`. Both engines use `importlib.import_module` lazy-loading, never a top-level `import`, to keep unit tests SDK-free and pyright green without the extra installed.

## Answers to the five questions

**1. New backend or new engine?** New **engine**: `engines/tensorrt.py` providing `TensorrtLlmTextBackend` (or similarly named), implementing the existing `backends/text.py::TextGenerationBackend` Protocol structurally — exactly the `llamacpp.py`/`vllm.py` pattern. No new Protocol in `backends/`. Confirmed correct per the existing `backends/` (contract) vs `engines/` (SDK-bound adapter) hierarchy, and per `text.py`'s own docstring already naming TensorRT-LLM as a Phase-4 implementer.

**2. Initial capabilities?** Chat/text-generation only (`chat.generate`), matching `catalog/entries/chat.py`'s existing `tensorrt_llm` rows. `vision.understand` also advertises `tensorrt_llm` in the descriptor/catalog, but wiring it is blocked by a separate, larger prerequisite: `VisionProvider` is entirely unwired today (no `backends/vision.py` Protocol exists, no vision Provider constructor fields) — that gap predates and is independent of this change (explicitly out of scope of `provider-backend-composition`). Embedding/rerank are not applicable — `tensorrt_llm` never appears in those catalogs, and `TextGenerationBackend` is chat-only by shape (`TextRequest`/`TextChunk`, not embedding vectors).

**3. Requirements introduced?** Researched externally (not previously in codebase): NVIDIA CUDA ≥12.2, an NVIDIA GPU, Python 3.10 per NVIDIA's documented environment (tension with this repo's Python ≥3.14 baseline — same kind of version-pin problem `vllm`'s `python_version < '3.14'` marker already works around; needs its own investigation/marker). TensorRT-LLM's modern Python API (`tensorrt_llm.LLM`) is architecturally closer to vLLM than to llama.cpp: `LLM(model=...)`, natively-async `generate_async(prompt, sampling_params, streaming=True) -> AsyncIterator[RequestOutput]`, `output.outputs[0].text` per-delta — this maps cleanly onto `VllmTextBackend`'s `AsyncLLMLike`/`RequestOutputLike` structural-Protocol pattern (single shared/refcounted engine, no thread-bridge), NOT onto llama.cpp's pool-of-N-blocking-instances pattern. Whether TensorRT-LLM's delta is cumulative or incremental (vLLM needed an explicit `RequestOutputKind.DELTA` to avoid O(n²) concatenation) is unverified and should be a design-phase open question. Heaviest constraint: engine-build (`trtllm-build`, or `LLM(model=hf_checkpoint)`'s JIT build path) takes 10-90 minutes per (model, GPU, dtype) combo, engines are not portable across GPUs, and no runtime model/quantization swap is possible — this makes on-demand engine construction at Worker boot a non-starter under this repo's own D27 pattern ("Startup viability validation = eager construction... boot time scales"); a multi-hour boot would be unacceptable. The design must consume a pre-built engine artifact path (mirrors `LlamaCppConfig.model_path` / `VllmConfig.model` — "the artifact IS its quantization" reasoning from D23/D19) and treat `trtllm-build` as an out-of-band operator step, never something `TensorrtLlmTextBackend.__init__` performs.

**4. What ModelSelectionPolicy needs?** Nothing new mechanically — `PreferenceOrderPolicy` already generalizes to N backends via `_BACKEND_PREFERENCE: tuple[BackendId, ...]` and `available_backends=frozenset(self.backends)` built from whatever's actually configured. `config.py` needs one more optional dataclass (`TensorrtLlmConfig`, mirroring `VllmConfig`'s shape: an engine-artifact path, matching `TextGenerationBackend`'s existing precedent — no new config *pattern*) and `worker.py` needs one more `if config.tensorrt_llm is not None: text[TENSORRT_LLM_BACKEND_ID] = TensorrtLlmTextBackend(...)` line plus a preference-order decision. Ranking relative to vLLM: TensorRT-LLM's own documented tradeoff (20-40% lower per-token latency at batch size 1, engine-build cost, no runtime model swap) suggests it is NOT a strict "prefer over vLLM" default — vLLM's continuous batching is likely still the safer default at concurrent load, and TensorRT-LLM is closer to "explicitly opt into, deployment declares intent" than "always prefer if configured." This preference ordering, and whether an operator-configurable preference beats a hardcoded one, should be an explicit `sdd-propose`/`sdd-design` decision (D-numbered), not assumed here.

**5. Explicitly out of scope (mirroring provider-backend-composition/proposal.md's own out-of-scope pattern):**
- Automatic model conversion/compilation into TensorRT engine format (`trtllm-build` or the `LLM(model=hf_checkpoint)` JIT path) — this change consumes an already-built engine artifact path, exactly as `llamacpp`/`vllm` consume already-quantized artifacts; building/compiling engines is an operator/ops-tooling concern, not a Worker responsibility.
- Distributed / multi-GPU / multi-node TensorRT-LLM serving (tensor/pipeline parallelism config) — single-GPU only, matching this repo's current single-process-per-Worker deployment shape; no config surface exists today for that either (vLLM/llama.cpp don't have it).
- `embedding.generate` / `rerank.documents` support — `tensorrt_llm` never appears in those catalogs; would need a wholly separate embedding/rerank Backend Protocol adapter, a distinct SDK surface, out of this change's blast radius.
- `vision.understand` support — `tensorrt_llm` IS in the vision descriptor/catalog already, but `VisionProvider` itself is unwired at the Provider-composition layer; wiring it needs its own prerequisite change (a `backends/vision.py` Protocol + wired `VisionProvider`) that doesn't exist yet, independent of TensorRT-LLM specifically. Out of scope here, in scope for a future change once vision wiring exists.
- Quantization runtime selection — same accepted limitation as `llamacpp`/`vllm` (D23): `ServingPlanLike` exposes only `.backend`, no Backend can act on `.quantization`; the artifact chosen at construction already fixes it.
- Pool-based concurrency (llama.cpp's shape) — TensorRT-LLM's Python API doesn't need per-session process-level pooling; if it needs any concurrency strategy at all beyond vLLM's single-shared-refcounted-engine shape, that's a design-phase investigation, not assumed pool reuse.
- Python 3.14 compatibility resolution — flagged as a real, unverified risk (NVIDIA docs reference Python 3.10); may need the same kind of `python_version` marker gymnastics `vllm`'s extra already has, or may block the extra entirely on this repo's toolchain until upstream catches up.

## Constraint validation (user's four-point architectural principle)

All four points HOLD, verified against real code, not assumed:
1. TensorRT-LLM implements the EXISTING `TextGenerationBackend` Protocol (`backends/text.py`) — confirmed generic enough (streaming `AsyncIterator[TextChunk]` already anticipates it in its own docstring); no Protocol change needed.
2. Integrates via the EXISTING `ModelSelectionPolicy`/`PreferenceOrderPolicy` — no new selection mechanism; adding a `BackendId` to `_BACKEND_PREFERENCE` and a config-gated dict entry is sufficient.
3. Constructed ONLY from `worker.py::build_runtime()` — enforced today by an AST constructor-call scan (`provider-backend-composition/spec.md`'s "Composition Root Exclusive Backend Ownership", corrected in D29 with the package-re-export carve-out already in place for `engines/__init__.py`); a new `TensorrtLlmTextBackend` re-export there is fine, a constructor call anywhere but `worker.py` is not.
4. `ChatProvider` requires ZERO code changes — confirmed by reading its full `execute()` body: no backend-name branching exists, only dispatch-mechanical conditionals (empty mapping, plan.backend absent, cancellation) already enumerated by `provider-backend-composition/spec.md`'s "No Selection Logic Inside Wired Providers" requirement, which any new backend entry trivially satisfies without touching this file.

## Recommendation

Pattern-match `engines/vllm.py`, not `engines/llamacpp.py`: single lazily-constructed, refcounted engine instance (TensorRT-LLM's `LLM`/executor is heavyweight-per-process like vLLM's `AsyncLLM`, not cheaply pool-of-N-instantiable like a GGUF `Llama` object), natively-async `generate_async(streaming=True)` needs no thread-bridge. `TensorrtLlmConfig` in `config.py` should mirror `VllmConfig`'s single-field shape (an engine-artifact path), not `LlamaCppConfig`'s pool-size shape. `sdd-design` must resolve: (a) delta vs cumulative token semantics, (b) Python-version compatibility marker, (c) preference ranking vs vLLM, (d) exact optional-dependency extra name and version pin.

## Risks

- Python 3.10 (TensorRT-LLM's documented baseline) vs this repo's Python ≥3.14 — unresolved, needs its own spike before `sdd-propose` commits to an extras-marker strategy.
- Engine-artifact provisioning (the 10-90 min `trtllm-build` step) has no place in this repo's deployment model today — must be explicitly named as an operator prerequisite, not silently assumed solved.
- Whether TensorRT-LLM's Python SDK is stably `pip`-installable without building from source is unclear from public docs (mixed signals: prebuilt wheel exists via `pypi.nvidia.com`, but full engine-build tooling may require source build) — verify before committing to a lazy-`importlib` extras pattern.
- CI/unit-test tier must stay SDK-free (no CUDA in test runners) — confirmed the existing engines already commit to this (stub-based unit tests + opt-in integration smoke tests); the new engine must follow the identical `testing/` fake + `tests/integration/test_tensorrt_smoke.py`-style pattern, not assumed but should be stated explicitly in the proposal.

## Ready for Proposal

Yes. All five questions are answered with codebase-grounded evidence, the user's four-point architectural constraint holds without modification, and the shape to follow (`engines/vllm.py`'s refcounted-single-instance pattern, `VllmConfig`-shaped config, one `worker.py` composition line, one `_BACKEND_PREFERENCE` entry) is concrete enough for `sdd-propose` to scope a slice plan.
